# 2026-09-29 — GitHub Pages: source versus build output

Status: implementation and verification record, not a claim of learner completion

Related lesson: [Builds and deployment](../lessons/11-build-and-deployment.md)

## The question

The owner made `Futtano/personal-website` public and selected “Deploy from a branch”. Why did the site still need a configuration change when GitHub reported a successful Pages publication?

## What we observed

The repository was public, and Pages was using `build_type: legacy` with source `main` at `/`. The branch-publishing run succeeded, but the served HTML still contained:

```html
<script type="module" src="/src/main.js"></script>
```

That was the source entry point. It did not contain the relative, fingerprinted asset URLs generated by Vite. Serving source does not resolve npm imports, transform Markdown imports, or package the scene.

An earlier custom-workflow run had failed at `actions/configure-pages` before Pages was properly configured. Its build was not the problem.

## Prediction

Selecting GitHub Actions and running the existing workflow should publish `dist/`, replace the source script with bundled assets, and make the interactive app work at the project subpath.

## The change

- Changed **Settings → Pages → Source** to **GitHub Actions** (`build_type: workflow`).
- Manually dispatched the existing `.github/workflows/deploy.yml` on `main`.
- Kept the workflow's Node 24 setup, locked install, build, artifact upload, permissions, and dependent deployment job.
- Kept Vite's relative `base: './'` for the project subpath.
- Updated current-status documentation; retained the original private-repository failure only as dated history.
- Kept `package.json`'s `private: true`, which prevents npm publication and does not control repository or site visibility.

The source and workflow already supported this deployment. No application-code or workflow-file change was required.

## Verification

Verified on 2026-09-29:

- Local `npm run build` succeeded.
- GitHub Pages reported `build_type: workflow`, a public site, and enforced HTTPS.
- Both build and deploy jobs succeeded in [run 36603166111](https://github.com/Futtano/personal-website/actions/runs/36603166111).
- The deployed source was commit [`6db416086421c52583c1ffdbe4679b0edde06c9e`](https://github.com/Futtano/personal-website/commit/6db416086421c52583c1ffdbe4679b0edde06c9e).
- The [live site](https://futtano.github.io/personal-website/) returned HTTP 200 and built HTML referencing `./assets/` bundles rather than `/src/main.js`.
- Referenced entry JavaScript and CSS returned HTTP 200 with the appropriate content types.
- All four [browser examples](../examples/README.md) passed against the live URL: direct article navigation, living-room computer interaction and article reading, narrow-screen layout, and reading without WebGL initialization.

Browser verification used Chromium with software graphics in the automation environment. It verifies these behaviors, not every device's GPU performance or the entire accessibility experience. The documentation edits for this entry are separate from the application commit deployed above.

## What this teaches

A successful publishing job proves that some files were published. It does not prove they were the right files. For this application the chain is source → Vite build → dist artifact → Pages deployment → live browser verification.

Repository visibility, npm package publication, Pages source configuration, and runtime behavior are separate concerns.

## Next experiment

For the next intentional app change, follow its main-branch commit through the automatic workflow and compare the built asset URLs before and after deployment. Continue running browser checks separately until we add them to CI.
